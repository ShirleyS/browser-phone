# Shared test phone with call allowances

User intent: an owner connects their own webhook/provider, shares a phone with testers, and can allow a single call or a few calls on top of existing limits. No signup for owner or tester. Forwarded links share the same allowance. Existing MojoAuth saved setups stay optional.

Owner Connect panel: Share a test phone; choices 1 call, 3 calls (default), 5 calls, Custom (integer1..100); expiry1hour/24hours(default)/7days capped by connection expiry. Only a verified current same-deployment webhook can create links. List existing links with calls used/limit, expiry and Revoke. Token returned once; copy full URL shown only immediately after create. Owner may create another if lost. Max20 active unexpired links/connection to keep list bounded. Creation uses connection bearer capability, never a provider key or login.

Tester URL `/test/{shareId}#key=bp_share_<43urlchars>`; fragment is read on mount and removed from address bar, kept only in isolated per-tab session storage. Referrer no-referrer and noindex metadata. Phone-only page, no workbench or owner controls, no owner connection capability/webhook URL/public agent ID returned. Each browser starts its own chat/call sessions using scoped share token. Display remaining calls and expiry. Opening/reloading does not consume quota. Starting a new call session consumes one total call attempt, including failures after reservation; no automatic refunds. Normal idempotent session retry does not consume again. Calls exhausted cannot silently become simulated calls on test page. Messages remain available until expiry subject to original daily session allowance. No existing conversation is shared.

Persist share token hash only in service-only RLS table bp_shares (id,connection_id,token_hash,settings JSON contact/lang,call_limit,calls_used,expires_at,revoked_at,created_at). Add nullable share_id to sessions. No encryption key needed because no owner/provider credentials are stored in share rows. Atomic RPC checks share+connection validity, row-locks shared allowance and calls existing bp_create_session in same transaction, preserving original fingerprint20/day/concurrency/duration. Namespace idempotency keys by share ID; reject cross-kind reuse and expired/ended replays. Create/rotate session phone tokens and persist callback token atomically before responding. Count only successful new call-session reservation. Cap session expiry/call deadline by link+connection expiry. Revoke denies all subsequent share/session/inbox/event/callback requests; browser ends active calls on next poll. Already-issued provider credentials cannot be recalled: documented limit governs Browser Phone call starts, not an absolute provider billing cap.

Public APIs (all bearer authenticated by handlers, bounded JSON, no-store):
- GET/POST `/connections/{id}/shares` with owner connection token. POST {settings:{contact:{name,number},lang},call_limit,expires_in_hours}; returns201 {share:summary,token}. GET {shares:summary[]}.
- POST `/connections/{id}/shares/{shareId}/revoke` owner token, returns {revoked:true}.
- GET `/shares/{id}` with bp_share_ token returns {settings,expires_at,usage:{used,limit,remaining,reset_at:expires_at,verified:true}}. Expired/revoked denied; exhausted may read info.
- POST `/shares/{id}/sessions` bp_share_ token, {kind:'chat'|'call'}, Idempotency-Key. Returns existing session response {id,kind,phone_token,expires_at,call_deadline,idempotent_replay}. Errors share_exhausted429,share_unavailable410,quota_exceeded429,etc.

Core handler integration: loadSession checks attached share active+unexpired. Shared call.start events normalized to a fixed ID and canonical request (no text) so another event ID cannot mint another voice credential from the same reservation. Uses existing delivery lease/replay. Owner sessions unchanged. Engine LiveConnection gains optional shareId; routes session create/usage accordingly; failed shared call shows error and ends rather than demo-success. Isolated usePhoneEngine mode prevents tester restoring/writing owner storage.

Builder decisions above (defaults, bounds and attempt-count semantics) are implementation choices. No new hosting purchases, live database migration, provider calls or Lovable publication claimed.
